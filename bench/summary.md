## 2. 环境探测中发现的两个关键事实（这两条是可信的）

### 2.1 代理与直连确实不同（已验证）

- DNS 解析一致：`100milionseek.top` → `[104.21.29.208, 172.67.149.205]`
- 出口 IP 不同（经 `api64.ipify.org` 探测）：
  - 直连出口：`125.112.182.6`（1260 ms 拿到响应）
  - 代理出口：探测请求本身 ECONNRESET，未能取到
- bun 的 fetch 代理控制语义（bun v26.3.0 / Bun 1.4.5）：
  - `proxy: null` / `proxy: ""` **不等于** 直连，仍走环境变量代理 → 实测超时
  - `proxy: false` 是**唯一**能强制直连的写法 → 实测 `ECONNREFUSED`（直连链路当时已不可用）
  - 结论：想在同一进程里对比两条路径，必须用 `fetch(url, { proxy: "http://127.0.0.1:7897" })` vs `fetch(url, { proxy: false })`，**不能**靠 `process.env.HTTPS_PROXY = undefined`（bun 启动时已快照环境变量）

### 2.2 该上游的绝对延迟极高（与代理无关）

单次 `max_tokens:8` 的 "reply OK" 请求，**首字节 15.5 s（走代理）/ 27.5 s（直连）**。这与题面给的初步数据（3.8–27.6 s）同量级，说明**基线延迟本来就在秒级到数十秒级**，不是压测打坏的。代理过载只是把它推到完全不可用。

## 6. 复测建议（代理恢复后）

1. **串行、单并发、请求间隔 ≥ 1 s**，绝不并发——本轮就是并发把 Clash 打挂的。
2. 每账号每路径 **3 次**，取中位数；先测完 19 个账号的 proxy 路径，再统一测 direct。
3. 每请求独立进程或显式 `proxy: false` 切换，避免 bun 环境变量快照问题。
4. 加 **连接复用**对照：同账号连发 5 次，看 run1（TLS 握手）vs run2–5 的 TTFB 差。
5. 加 **长输出组**（`count from 1 to 100`, `max_tokens:400`）分离"首字慢"与"吐字慢"。
6. 测量前先 `curl -x proxy https://www.gstatic.com/generate_204` 探活，`code=204` 才开跑。
